# Agent 控制舱能力地图与演进基线

> 状态：阶段一、二完成，阶段三待实施
>
> 更新日期：2026-08-07
>
> 适用范围：BinnAgentX 控制舱、Control API，以及 Agent 运行、治理、复核和质量观测能力。

## 1. 结论

当前控制舱已经覆盖内容生产、Agent 目录、Tool 治理、Prompt 治理、体验访问和用户管理，但整体仍偏向“配置与内容后台”。一个完整的 Agent 控制舱还必须回答四类问题：

1. Agent 现在运行到哪里，为什么暂停或失败；
2. 调用了哪些 Tool、模型和 Prompt，花费多少，是否降级或重放；
3. 哪些结果正在等待人工决策；
4. 新版本是否比旧版本更可靠，是否满足发布门槛。

新增界面必须扩展现有控制舱和既有领域链路，不得复制 Workflow、复核状态机、审计账本或内容生产流程。

## 2. 当前已展示能力

| 模块 | 当前能力 |
| --- | --- |
| 内容与 Agent | 公共材料生成、个性化材料运行、Worker 状态、失败恢复、发布、Langfuse 链接 |
| Agents | 静态 Agent 目录、Prompt/Tool 依赖、依赖阻塞和检查点能力 |
| Tools | 注册 Tool、Schema、风险、权限和持久化启停策略 |
| Prompts | Prompt 版本、编辑、创建和激活 |
| 体验访问 | 体验码创建、容量和撤销 |
| 用户管理 | 用户、会话和基础资源计数 |

## 3. 尚未展示的核心模块

### P0：运行与治理闭环

#### 3.1 Agent 运行中心

复用现有 `workflow_runs`、task refs、domain events 和 run replay，展示：

- run、学习者隔离标识、运行类型、生命周期、阶段和版本；
- 当前任务、检查点、模型调用次数和累计费用；
- 任务链、匹配决策、完成缺口和脱敏事件时间线；
- 已有的人工校准 fallback 与检查点恢复入口。

不得创建第二套运行表或控制端专用状态机。

#### 3.2 Tool 与模型调用中心

复用 `model_invocations`、`model_invocation_ledger` 和 `tool_usage_ledger`，展示：

- Agent、Tool、Prompt 版本、invocation key 和关联 run/task；
- 成功、拒绝、fallback、可重试和终止错误；
- 耗时、调用次数、估算/实际费用和结果重放状态；
- reason code、版本前后值和审计事件引用。

正文、完整 Prompt、密钥和隐藏推理不得进入普通控制视图。

#### 3.3 人工复核收件箱

复用现有知识提案审核、内容发布门、校准 fallback 和个性化材料检查点恢复链路，形成按类型聚合的收件箱。控制舱只负责查询和发出既有领域命令，不自行修改业务状态。

#### 3.4 审计与事件中心

复用 `audit_events`、`domain_events`、`idempotency_records` 和 `outbox_messages`，按 run、task、Tool 和时间查询状态变化。审计结果、业务事件和消息投递必须分别展示，不能混成一条含义不明的日志。

### P1：记忆、成本与质量

#### 3.5 Memory / Knowledge 中心

展示账号隔离的工作记忆、长期学习资产、Obsidian 同步连接、组织运行、知识候选、关系、提案及来源证据。默认只展示摘要和引用，不展示完整私人笔记。

#### 3.6 预算与模型策略

展示每个 Agent、Tool 和 run 的调用次数、Token/费用、预算占用、供应商状态、超时和 fallback 比例。配置变更必须版本化并保留审计。

#### 3.7 Agent 评测中心

展示 Schema 通过率、任务成功率、fallback 率、轨迹合规、Prompt 回归、版本对比和发布门。Langfuse 是调用追踪来源之一，不能代替业务正确性评测。

### P2：学习证据与系统治理

#### 3.8 学习证据与能力状态

展示阅读、语法、词汇和表达证据，区分独立、受提示、未验证和冲突状态，并关联下次复习时间。该页面只投影现有学习证据，不允许控制端直接改写能力值。

#### 3.9 系统策略与安全

展示 Feature Gates、Actor/Scope 权限矩阵、人工审批要求、连接健康和策略变更历史。密钥只展示是否已配置，不显示内容。

#### 3.10 通用队列与基础设施

把内容 Worker 之外的 Outbox、后台任务、租约、积压、重试和死信纳入统一运行观测，但继续由各自既有 Worker 执行。

## 4. 现有页面内部缺口

1. Tools 页面尚未完整显示预期版本范围、调用计数、审计策略、超时、每 run 上限和 fallback 策略；
2. Agents 页面展示的是目录和依赖可用性，不是 Agent 运行实例；
3. Prompts 已有 render API，但界面缺少变量试填、渲染预览、版本 diff 和激活前回归；
4. 内容页面只有内容相关运行，未覆盖学习运行、Tool 调用和通用后台任务；
5. Langfuse 目前以外链存在，未与本地 run、Tool、审计和费用形成统一索引。

## 5. 信息架构

建议在不拆分第二套应用的前提下，把现有控制舱逐步整理为：

```text
运行中心
  ├── 学习运行与回放
  ├── 内容运行
  └── Tool / 模型调用

治理中心
  ├── 人工复核
  ├── 审计与事件
  ├── 预算与模型策略
  └── 系统策略与安全

资产中心
  ├── Agents
  ├── Tools
  ├── Prompts
  └── Memory / Knowledge

质量中心
  ├── Agent 评测
  └── 学习证据与能力状态
```

## 7. 完成标准

一个新控制模块只有同时满足以下条件才算完成：

1. 查询和命令复用既有领域聚合、API 和权限边界；
2. 默认脱敏并保持学习者数据隔离；
3. 所有控制命令具有预期版本、幂等或人工审批中适用的约束；
4. 页面显示真实持久化状态，不使用静态示例冒充运行状态；
5. 后端集成测试和前端交互测试覆盖成功、空状态、权限拒绝和冲突；
6. 文档中的实施状态与代码保持一致。
